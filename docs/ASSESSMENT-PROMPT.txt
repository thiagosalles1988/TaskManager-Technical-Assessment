==================================================
1. PROJECT OVERVIEW
==================================================

Project name: TaskManager

Build a responsive web application where registered users can securely manage their personal tasks.

User Story:

"As a registered user, I want to create, view, update, organize, and delete my personal tasks so that I can efficiently manage my daily responsibilities."

Acceptance Criteria:

- A user can register with an email and password.
- A registered user can authenticate and receive a JWT.
- User information is persisted in the database.
- Authenticated users can create tasks.
- Authenticated users can view their tasks.
- Authenticated users can update their tasks.
- Authenticated users can delete their tasks.
- Tasks contain a title, description, status, and due date.
- Every task is associated with its owner.
- Users cannot read or modify another user's tasks.
- Invalid requests return meaningful errors.
- The frontend provides a responsive and intuitive interface.
- The application includes demo credentials and seed data.
- The solution includes automated tests and technical documentation.

Keep the product scope intentionally small. Prioritize engineering quality over unnecessary features.

4. DATABASE DESIGN
==================================================

Create at least two tables:

Users:
- Id (uniqueidentifier, primary key)
- Email
- NormalizedEmail
- PasswordHash
- CreatedAtUtc

Tasks:
- Id (uniqueidentifier, primary key)
- UserId (foreign key)
- Title
- Description
- Status
- DueDateUtc
- CreatedAtUtc
- UpdatedAtUtc

Requirements:

- Define appropriate SQL types.
- Use proper primary and foreign keys.
- Enforce unique normalized email addresses.
- Add appropriate indexes.
- Use UTC timestamps consistently.
- Use database constraints where appropriate.
- Never store plain-text passwords.
- Use a secure password hashing implementation.
- Never store secrets in source control.

Provide versioned SQL scripts for database creation and schema initialization.

Provide a repeatable, development-only seed mechanism.

Create a demo user and sample tasks for evaluation.

Document the demo credentials in README.md and make it clear that they are for development only.

Use environment variables or .NET user secrets for sensitive configuration.

If an existing SQL Server instance is available, support it through a connection string.

Optionally provide Docker Compose for local SQL Server setup, but do not make Docker mandatory when an existing SQL Server instance is available.

5. DATA ACCESS WITH RAW ADO.NET
==================================================

Use Microsoft.Data.SqlClient directly.

Implement:
- IUserRepository
- ITaskRepository

Repository operations must use:
- SqlConnection
- SqlCommand
- SqlParameter
- SqlDataReader
- Async database methods
- CancellationToken where appropriate
- Proper connection and command disposal

All SQL queries must be parameterized.

Never concatenate untrusted input into SQL commands.

Implement explicit mapping between database rows and domain entities.

Ensure user ownership is enforced at the database query level for task operations whenever applicable.

For example, updating a task must require both:
- TaskId
- Authenticated UserId

Avoid reading a task without ownership validation and then trusting the client to update it.

Do not introduce a custom ORM or overly complex data access framework.

Use transactions only when operations require atomicity.

6. AUTHENTICATION AND AUTHORIZATION
==================================================

Implement JWT Bearer authentication.

Endpoints:

POST /api/auth/register
POST /api/auth/login

GET /api/users/me
GET /api/public/info

Requirements:

- Registration persists users.
- Email validation.
- Email uniqueness.
- Secure password hashing and verification.
- JWT token generation after successful login.
- Configurable issuer, audience, signing key, and expiration.
- No hardcoded production secrets.
- Authorization using [Authorize].
- Public endpoints using [AllowAnonymous].
- User identity obtained from verified JWT claims.
- Invalid credentials return HTTP 401.
- Duplicate registration returns an appropriate conflict response.
- Never expose password hashes.

Use the established ASP.NET Core authentication middleware.

Do not create custom cryptography.

For this assignment, provide separate authentication and task API controllers within the same ASP.NET Core host.

Document why separate API controllers were chosen instead of deploying separate services.

7. TASK MANAGEMENT API
==================================================

Implement the following endpoints:

GET    /api/tasks
GET    /api/tasks/{id}
POST   /api/tasks
PUT    /api/tasks/{id}
DELETE /api/tasks/{id}

All task endpoints require authentication.

Use appropriate HTTP status codes:

200 - Successful retrieval
201 - Resource created
204 - Successful update or deletion
400 - Validation failure
401 - Missing or invalid authentication
404 - Resource not found or not owned
409 - Conflict when applicable
500 - Unexpected server errors

Use consistent error responses, preferably ProblemDetails.

Never expose exception stack traces in production responses.

Task validation:

- Title is required.
- Title maximum length: 120 characters.
- Description maximum length: 2000 characters.
- Status must be a supported value.
- Due date must be a valid date when provided.
- A task must always belong to a user.
- UserId must never be trusted from the client request.

Supported task statuses:
- Todo
- InProgress
- Completed

Do not add unnecessary business rules that prevent legitimate overdue tasks.

Use consistent request and response DTOs.

Return task information without exposing sensitive user data.
